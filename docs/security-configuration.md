# Сертификаты, редиректы и вложения

Настройка дополнительного доверия для приложений, использующих CraftTalk iOS SDK.
[Основное подключение](../README.md).

## Корневое доверие и разрешённые переходы

Добавьте публичный корневой сертификат `RootCA.cer` в ресурсы target приложения
(Target Membership / Copy Bundle Resources). Загрузите его перед настройкой:

```swift
guard let url = Bundle.main.url(forResource: "RootCA", withExtension: "cer") else {
    throw CocoaError(.fileNoSuchFile)
}
let rootDER = try Data(contentsOf: url)
```

Передайте корень и разрешённые хосты:

```swift
let security = CTSecurityConfiguration(
    trustedRootsByHost: ["chat.example.com": [rootDER]],
    allowedRedirectHosts: ["chat.example.com"]
)
try CTChat.shared.configure(security: security)
```

Два списка независимы:

- `trustedRootsByHost` добавляет корневые CA только для указанного хоста. Системные
  CA продолжают работать. Проверяются имя сервера, срок и цепочка сертификатов.
  Доверие корню позволяет заменять серверный сертификат под тем же корнем.
- `allowedRedirectHosts` разрешает HTTPS-переходы внутри чата и редиректы нативных
  запросов. Исходный хост из `CTChatBaseURL` добавляется автоматически. Смена пути
  и порта разрешена; каждый следующий хост проверяется отдельно. Добавление корня
  **не разрешает** навигацию на его хост.

Указывайте точные ASCII DNS-имена (IDN в punycode) или IPv4, без схемы, порта,
пути, пробелов и `*`. Регистр и одна завершающая точка DNS нормализуются.
`chat.example.com` не разрешает `sub.chat.example.com` или похожее имя.

Значения сертификатов — бинарный **DER** (`Data`), не PEM и не текст base64.
Расширение файла может быть `.cer`, `.der` или `.crt`; важно его содержимое.
Передавайте корни CA, а не серверные сертификаты или всю цепочку для сравнения.
Настройки других сетевых библиотек автоматически не наследуются. Системное хранилище
сертификатов SDK не изменяет; исключения ATS не нужны.

`configure(security:)` синхронно проверяет хосты, непустые наборы корней и читаемость
сертификатов, а также HTTPS-адрес `CTChatBaseURL`. Ошибка выбрасывается до применения
политики. Предыдущая политика при этом сохраняется. Пустая
`CTSecurityConfiguration()` выбирает новый режим с системным доверием.
Настраивайте SDK до открытия чата. Смена политики при активных соединениях не поддерживается.

## Ограничения инициализации

**Существующая асинхронность сохраняется:** проверка политики синхронная, но чтение
URL, namespace и salt выполняется на фоновой очереди, как и раньше. API пока
не сообщает о завершении этой инициализации. Немедленная регистрация посетителя
может вычислить hash до её окончания, а немедленное открытие чата — получить пустой
URL. Кроме того, прежний код читает salt по ключу `CTChatBaseURL` вместо `CTSalt`.
Обе проблемы остаются отдельной задачей; пример не является их исправлением.
Не обходите их присваиванием внутренних полей SDK.

## Навигация и ошибки

В новом режиме автоматический переход на посторонний хост или HTTP отменяется.
Пользовательская ссылка из главного фрейма на внешний HTTP(S)-сайт открывается
через существующий `SFSafariViewController`. Фоновая навигация iframe и
автоматические редиректы внешний браузер не открывают. Программный `a.click()`
не считается пользовательским нажатием; разрешённая ссылка не даёт разрешения
на последующий редирект к постороннему хосту. Сохраняются `tel:`, `mailto:`
и загрузка `blob:`. Разрешённые ссылки с новым окном открываются в текущем чате.

В новом режиме вложения (`Content-Disposition: attachment`, атрибут `download`
и ответы с содержимым, отличным от HTML) сохраняются во временный файл и открывают
системное меню сохранения/отправки. Страница чата, её сессия и черновик остаются
на месте. Для постоянного хранения выберите «Сохранить в Файлы»; временный файл
удаляется после закрытия меню. Ссылки с целью iframe также поддерживаются;
обычные HTML-переходы и отображаемые ресурсы iframe продолжают загружаться в нём.
Ответы-вложения из iframe обрабатываются по тем же правилам TLS и редиректов,
что и загрузки из основного документа; они не открывают Safari.
На iOS 18.2+ дополнительно отменяются загрузки из iframe, которые WebKit
отмечает как не инициированные пользователем. Ограничения WebKit на сторонние
cookies в iframe сохраняются.

На iOS 14.5+ загрузка продолжает исходный запрос через `WKDownload`, сохраняя
cookies и тело запроса без повторной отправки. На более старых системах GET-ссылка
перехватывается **до первого запроса**, если у неё есть атрибут `download`, известное
расширение файла (например, `.zip`) или путь SDK с компонентами `webchat` и `file`.
Загрузку выполняет защищённая `URLSession`; на iOS 11+ cookies берутся из WebView.
Это сохраняет одноразовые ссылки, включая ссылки без расширения на файловый endpoint SDK.
Произвольный URL без этих признаков нельзя распознать заранее: если старый WebKit
получит ответ-вложение, SDK отменит его с `onError` (`download`, `NSURLErrorDomain`,
`-1002`), **не отправляя повторный GET**. Для таких ссылок веб-виджету нужен атрибут
`download`. POST также не повторяется. Минимальная версия проекта не повышена.
Проверка каждого редиректа и TLS действует также для вложений; ошибку получает
`onError`, после неё можно повторить загрузку. Старый `configure()` сохраняет
прежнее открытие ссылок во внешнем просмотре.

Политика навигации не является фильтром всех ресурсов страницы: загрузка скриптов,
изображений, fetch/XHR и WSS подчиняется TLS и правилам WebKit (в том числе CORS).
Для отдельного хоста ресурсов с частным CA добавьте корень в `trustedRootsByHost`.
Список редиректов нужен, если на хост осуществляется навигация или нативная загрузка.

`CTChat.shared.onError: ((Error) -> Void)?` получает ошибки загрузки, TLS и
запрещённых переходов на главной очереди. `CTChatError` содержит `stage`, `host`,
`domain` и `code`, без пути, query, токенов, посетителя и тела запроса.
В новом режиме callback получает и ошибки системной TLS-проверки ресурсов
на хостах без дополнительных корней. Решение о системном доверии остаётся за платформой.
Одна неудачная операция может дать TLS-ошибку и последующую ошибку отменённой загрузки.
Ошибки JavaScript/CORS сами по себе не являются navigation callbacks WebKit;
веб-виджет должен обрабатывать их своими средствами.

| Домен / код | Значение |
|---|---|
| `CTChat / 1` | Некорректный хост конфигурации |
| `CTChat / 2` | Пустой набор корней для хоста |
| `CTChat / 3` | Нечитаемый DER-сертификат |
| `CTChat / 4` | Некорректный или не-HTTPS `CTChatBaseURL` |
| `CTChat / 5` | Запрещённый адрес/переход |
| `CTChat / 6` | Другая загрузка или просмотр вложения ещё выполняется |
| `HTTP / status` | Нативный сервер вернул статус вне 2xx |
| `NSURLErrorDomain`, `WebKitErrorDomain` | Ошибка платформы; TLS-проверка SDK сообщает `-1202` |

Нативный запрос сохраняет метод и тело редиректов 307/308 через механизм Foundation.
SDK не переносит вручную авторизационные заголовки между хостами. При любой ошибке
состояние загрузки освобождается до callback, чтобы повтор мог начаться сразу.

## Старый `CTCertificate`

`CTChat.shared.configure()` без аргумента сохраняет прежний режим: файл
`CTCertificate.cer` / `.der` / `.crt` сравнивается с leaf-сертификатом основного
WebView. Это старый pinning, а не добавление доверенного корня; его прежняя
семантика проверки и выбор хостов сохранены, включая IPv6 и внутренние имена.
Строгая нормализация хостов применяется только в новом API. Нативная URLSession в старом режиме использует
системное доверие, как раньше.

`configure(security:)` **не читает и не применяет `CTCertificate`**, даже если он
присутствует в bundle. Новый режим следует использовать для сценария с корневыми CA.


Закрытые Shadow DOM, созданные через `attachShadow`, поддерживаются.
Декларативный `<template shadowrootmode="closed">` механизм наблюдения за ссылками
не охватывает.
