# Как писать и ревьюить тесты SDK

Это правила качества тестов для разработчика и агента. Команды, окружения и
манифесты находятся в [CI и тестировании](ci-and-testing.md), незакрытые сценарии
и результаты матрицы — в [плане покрытия](testing-plan.md). Не дублируйте здесь
числа тестов, проценты покрытия и историю прогонов.

## Проверяемый контракт

- Перед тестом определите наблюдаемый результат и конкретную ошибку, которую он
  должен обнаружить. Имя теста не должно обещать больше, чем его assertions.
- Эталон должен быть независимым: фиксированные байты/hash, документированный
  результат, журнал принимающего сервера. Не вычисляйте ожидаемое значение тем
  же helper, который проверяете.
- Проверяя сохранение страницы/черновика, измените черновик после загрузки и
  контролируйте повторные запросы страницы либо её уникальный идентификатор.
  Исходное значение input из HTML появится заново и после ошибочной перезагрузки.
  После закрытия меню проверьте доступность поля и продолжение ввода через XCUITest:
  сохранённый DOM не доказывает, что WebView остался на экране. Для JS-проверок ждите
  чтения, начатого после проверяемого действия; при ошибке чтения очищайте прежний
  снимок и публикуйте причину, а не выдавайте кеш за текущее состояние.
- У отрицательного сценария проверьте причину отказа и достижение нужного этапа.
  Любая ошибка, отсутствие файла сразу после старта или просто отсутствие crash
  не доказывают правильный отказ. Для TLS проверяйте также успешный контрольный
  сценарий; для запрета запроса — журнал заведомо доступного тестового сервера.
- Для особенно рискованной регрессии полезна локальная проверка чувствительности:
  временно отключить защищающий код в изолированной копии и убедиться, что тест
  падает по нужной причине. Не изменяйте для этого чужое рабочее дерево и не
  оставляйте мутацию в итоговом diff. Полный mutation testing не обязателен.
- Characterization-тест существующего ограничения не превращает его в желаемый
  контракт. Сошлитесь на ограничение в плане; не ослабляйте regression assertion
  ради зелёного результата и не исправляйте SDK вне согласованного объёма задачи.

## Выбор уровня

| Что защищаем | Подход |
| --- | --- |
| Разбор, нормализация, выбор имени, сериализация | Изолированный XCTest с граничными значениями |
| Формирование запроса и планирование push | Отдельные URLSession/URLProtocol и управляемый планировщик |
| TLS, редиректы, cookies, фактические GET/POST | Настоящий URLSession и локальный HTTPS-стенд |
| WebKit delegate, JS-мост, жесты, меню, жизненный цикл | Настоящий контроллер SDK в host и XCUITest |
| Производительность, память, аппаратные функции, внешние сервисы | Отдельная проверка на подходящем устройстве/стенде |

URLProtocol не подтверждает TLS и поведение WebKit. Ручной вызов delegate
проверяет его ветвление, но не доставку callback системой. Отдельный WKWebView,
к которому тест вручную подключил обработчик, не подтверждает жизненный цикл
WebView, созданного самим контроллером. Для публичной интеграции оставляйте
проверки без обхода configure, Bundle.main и публичного CTVisitor.

XCTest остаётся допустимым для этого проекта; переход на Swift Testing не является
условием качественных тестов. UI-тесты используют XCTest/XCUIAutomation. При выборе
тестового фреймворка учитывайте поддерживаемый toolchain.

## Асинхронность и изоляция

- Ждите события с ограниченным timeout. Получение запроса сервером не означает,
  что клиент уже обработал тело ответа. Для конкуренции фиксируйте порядок именно
  тех событий, взаимодействие которых проверяете; sleep не заменяет барьер.
  Таймаут удерживаемого ответа стенда должен прерывать ответ и проваливать прогон;
  он не заменяет явный `release`. Сброс сценария и завершающая уборка отменяют
  ожидания, но не стирают уже зарегистрированные ошибки стенда.
- Проверяйте число callbacks там, где это часть контракта. Завершайте/отменяйте
  операции и дожидайтесь остановки сессий до освобождения тестовых ресурсов.
- Код UIKit/WebKit исполняйте на главном потоке; для async XCTest явно используйте
  `@MainActor`, если он необходим. Не блокируйте executor, нужный ожидаемому callback.
- Каждый сценарий должен начинаться с собственного состояния файлов, cookies,
  серверных маршрутов и callbacks, в том числе после падения предыдущего теста.
  `XCUIApplication.terminate()`/`launch()` не очищают контейнер приложения.
  Serial execution само по себе не обеспечивает изоляцию.
- Сначала проверьте cleanup самого SDK и сохраните диагностику, затем выполните
  уборку стенда. Уборка тестом не должна выдавать себя за корректный cleanup SDK.
  Следующий запуск должен изолироваться и после crash, когда teardown не вызван.
- Проверка удаления вложения включает его файл **и принадлежащий ему каталог**.
  Ошибка чтения каталога/файла в наблюдателе — диагностическая ошибка, а не пустой
  список. Наблюдение не должно молча скрывать остаточные файлы.
- Для нестабильного сценария используйте отдельный повтор до первого сбоя или
  фиксированное число повторов; сохраняйте исходное падение. Проверка в случайном
  порядке помогает обнаруживать зависимости. Текущий CI-манифест требует одного
  выполнения каждого теста: диагностические повторы не выдавайте за полный прогон.

## Доказательства и ограничения

Проверяйте exit code и фактически выполненные идентификаторы/результаты в xcresult,
а не только успешную сборку или число строк `test` в исходниках. При изменении
набора обновляйте соответствующий манифест осмысленно. Для CI-инфраструктуры
проверяйте также отрицательные входы: отсутствующий/пропущенный/упавший тест,
ошибку запуска и сохранение артефактов.

Покрытие строк помогает найти непроверенный код, но не подтверждает assertions,
ветки, JS и правильность поведения. Сборка Debug и один Simulator runtime не
подтверждают весь диапазон iOS, Release, реальные устройства или Firebase/APNs.
В отчёте указывайте фактические Xcode/runtime, полный набор или поднабор и пробелы.
