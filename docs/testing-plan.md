# План покрытия CraftTalk iOS SDK тестами

Цель — максимально покрыть бизнес-логику и все поддерживаемые пользовательские
сценарии SDK: успешное выполнение, ошибки, отмену, повтор, конкуренцию операций
и жизненный цикл. Процент покрытия помогает находить пробелы, но не заменяет
проверку наблюдаемого поведения. Тесты должны обнаруживать нарушение контракта,
а не закреплять устройство текущей реализации или известные дефекты.

Статус: инфраструктура этапов 0–3 реализована; действуют 121 SPM-тест и 42 UI-теста.
Новый тест отмены интерактивного закрытия legacy-preview выявил дефект и остаётся
падающим: текущий UI-набор не зелёный, исправление SDK в эту задачу не входит.
Исправления этапа 0 сохранены. Изменения поведения из этапов 1 и 3 отменены;
часть требований этапа 3 остаётся незакрытой из-за исходных дефектов SDK.
После повторного ревью отдельно согласовано исправление цикла удержания WebView:
все регистрации JS-обработчиков переведены на слабого посредника.
Этап 4 выполняется частично на локальных симуляторах. Команды и действующая инфраструктура описаны
в [CI и тестировании](ci-and-testing.md), текущие контракты — в

## Правила покрытия

- Для каждой возможности вести связь «сценарий → ожидаемый результат → тест →
  окружение → статус». Отмечать отдельно автоматизированные проверки,
  проверки на стенде/устройстве и незакрытые пробелы с причиной.
- Проверять существенные границы данных и сочетания состояний. Для рискованных
  взаимодействий явно проверять комбинации: POST + редирект + вложение,
  cookie + смена хоста, ошибка + немедленный повтор, закрытие чата + загрузка.
- На этапах покрытия сохранять существующее поведение. Найденные старые дефекты
  описывать отдельно; исправления требуют отдельной задачи. Исключение — уже
  согласованные исправления этапа 0. Тесты текущего поведения не означают, что
  ограничения устранены или что такое поведение рекомендуется интеграторам.
- Если падение завершает тестовый процесс, воспроизвести его в отдельном процессе
  или отметить проверку как незакрытую. Не менять SDK для устранения падения
  в рамках покрытия; для исправлений этапа 0 проверить и исходный пользовательский путь.
- Сохранять публичный API и legacy-путь. Внутренние зависимости выделять
  точечно по потребностям тестов. Изменения контракта документировать отдельно
  от перестройки кода для тестируемости.
- Проверять собственный код SDK, Example и скриптов. Для WebKit, UIKit,
  Foundation и Pods проверять используемые интеграции, а не внутренности библиотек.
- Реальные сетевые проверки не подменять вызовами delegate вручную. Тесты TLS
  не должны отключать проверку доверия или добавлять ATS-исключения.

## Этап 0 Исправление известных дефектов с регрессионными тестами

- [x] Чтение `CTSalt`: проверить настройки, где URL и salt заведомо различны,
  и ожидаемый hash по независимому контрольному значению. Затем исправить ключ.
- [x] Инициализация: определить детерминированный контракт готовности для
  `configure()` и `configure(security:)`, сохранив сигнатуры публичных методов.
  Предпочтительный результат — после успешного возврата можно сразу создать
  посетителя и открыть чат с полностью применёнными настройками. Проверить
  совместимость такого изменения до реализации; не маскировать гонку задержкой.
- [x] Проверить отсутствие частично применённой конфигурации, сохранение
  предыдущей политики при ошибке нового режима, повторную настройку до открытия
  чата и поведение при отсутствующих/некорректных значениях Info.plist.
- [x] Blob: проверить неверный тип сообщения, пустую строку, отсутствующие
  разделители, неизвестный MIME, некорректный base64, пустые и корректные данные.
  Определить результат для неизвестного MIME; исключить падения и частичные файлы,
  обеспечить очистку и возможность следующей загрузки.
- [x] Добавить тесты исправлений, синхронизировать SDK, выполнить SPM build/test
  и Example build. Обновить описания ограничений только после исправления.

Результат этапа: исправления сопровождаются тестами правильного поведения.
Независимые тесты следующего этапа можно добавлять до завершения всех исправлений.

## Известные ограничения без исправлений

После пересмотра объёма задачи SDK возвращён к поведению до этапов 1 и 3.
Оставлены подстановки зависимостей для тестов и исправления этапа 0.
Следующие проблемы не исправляются в задаче покрытия:

- **Push:** каждый вызов ставит отдельную отправку; токен/UUID захватываются сразу.
  Смена данных не отменяет старые запросы, тело сообщения моста не фильтруется.
  Это проверяется компонентными тестами как существующее поведение. При непустом
  токене и отсутствии посетителя разыменовывается nil; падение в отдельном процессе
  пока не автоматизировано. Появление первого токена после события само не запускает push.
- **Посетитель:** customProperties могут заменить UUID/hash в JSON, не меняя
  нативного посетителя; это может рассогласовать виджет и push. Проверяется текущий
  приоритет полей, запрет переопределения не добавляется.
- **Адреса и имена:** завершающий slash сохраняется и создаёт двойной slash в пути.
  Push request использует исходный URL-конструктор с force unwrap. Имена файлов
  обрабатываются через Unix `lastPathComponent`; очистка Windows-разделителей и
  управляющих символов не добавляется. Для '/' возможна ошибка записи вместо файла.
- **Меню отправки:** программное закрытие чата поверх меню может оставить файл;
  успешная очистка в этом сценарии не заявляется. Исправление цикла удержания
  контроллера не заменяет проверку очистки уже показанного меню.
- **Новое окно:** отказ вложения `target="_blank"` на iOS 18.6 воспроизведён на этапе 3;
  поддерживавшее этот случай изменение originatingFrame отменено. В рабочем наборе
  проверяются iframe-вложения и HTML-навигация с новым окном; успешное скачивание
  через новое окно остаётся незакрытым требованием.
- **Отмена закрытия:** удаление активных передач из viewWillDisappear, добавленное
  на этапе 3, отменено. Новый `testCancelledInteractiveBackPreservesLegacyPreview`
  воспроизвёл дефект: настоящий переход начинается и отменяется, чат/WebView живы,
  но каталог и файл preview уже удалены. `viewWillDisappear` вызывает
  `closeBlobPreview` до завершения перехода. Тест оставлен падающим, SDK не изменён.

Проверка исходных контрактов выполняется без skip/expected failure и без ослабления
проверки состава результатов. Неподдерживаемые сценарии перечислены здесь отдельно;
предыдущий зелёный набор не означал устранения этих дефектов. Новый тест отмены
закрытия включён в основной манифест и делает его красным до исправления SDK.

## Этап 1 Бизнес-правила и изоляция зависимостей

- [x] Политика адресов: регистр, завершающая точка, длины DNS-имён и меток,
  punycode, IPv4, некорректные хосты, схемы, credentials, порты, поддомены
  и похожие имена. Корни доверия и разрешённые переходы независимы.
- [x] Конфигурация корней: пустые наборы, некорректный DER, нормализованные
  совпадающие хосты; коды и этапы ошибок.
- [x] Посетитель: hash, порядок полей, Unicode, nil/пустые значения, явный hash,
  JSON, вложенные customProperties и недопустимые значения. Зафиксировать
  ожидаемое поведение при совпадении customProperties со стандартными ключами.
- [x] Push: формирование URL, метода, заголовков и тела; отсутствие отправки
  без токена; привязка к посетителю и поведение при повторных событиях JS.
- [x] Диагностика: stage/host/domain/code, отсутствие пути, query, токенов,
  тела запроса и данных посетителя, доставка callback на главной очереди.
  Не требовать ровно одного onError там, где контракт допускает TLS-ошибку
  и последующую ошибку отменённой операции.
- [x] MIME и тип preview, поиск ресурсов сертификатов и приоритет bundle,
  распознавание ссылок на вложения, существующие правила basename/fallback.
- [x] Добавить необходимые внутренние способы передачи настроек, сетевой
  конфигурации, планировщика задержек и файлового окружения. Изолировать
  состояние CTChat.shared; фоновые операции не должны переживать свой тест.

Результат этапа: самостоятельные правила проверяются воспроизводимо,
без внешнего сервера, зависимости от порядка тестов и произвольных sleep.
