# CI и тестирование

Порядок расширения покрытия и статус этапов: [план тестирования](testing-plan.md).
Правила написания и ревью тестов: [качество тестов](testing.md).

## Что проверяет CI

Workflow `CI` запускается для каждого pull request, push в `master` и вручную
через `workflow_dispatch`. Он выполняет сборки SDK/Example, Python-проверки и проверку копий.
Все Swift XCTest требуют iOS Simulator; они запускаются локально в `pre-push`,
а в Actions — **только вручную** в отдельном workflow `Simulator tests — manual`
([simulator-tests.yml](../.github/workflows/simulator-tests.yml)). Он сначала проверяет
копии SDK и Python helpers, затем запускает SDK-тесты и четыре UI-части.
Имена workflows входят в concurrency-группы. Обычный push и ручной прогон
симуляторов используют разные группы. Новый запуск с тем же ключом PR или
ветки отменяет предыдущий запуск того же workflow.

| Проверка | Окружение | Действия |
| --- | --- | --- |
| Check SDK matches its copy in Example | Ubuntu 24.04, Python 3 | Совпадение 1:1 путей и содержимого всех `.swift` в `CTChat/` и `Example/Chat/CTChat/` |
| Build SDK | macos-15-intel, Xcode 16.4 | Сборка пакета `CraftTalk` для iOS Simulator |
| Test SDK (только вручную) | macos-15 (Apple Silicon), Xcode 16.4 | XCTest на iPhone 16 / iOS 18.6 |
| Test WebKit user flows (1/4–4/4, только вручную) | macos-15-intel, Xcode 16.4 | Четыре части XCUITest на iPhone 16 / iOS 18.6 |
| Build Example app | macos-15-intel, Xcode 16.4 | Debug-сборка схемы `Chat` для устройства без подписи |

В обычном `CI` jobs с симуляторами отсутствуют, поэтому нет строк `skipped`
для этих тестов. Зелёный `CI` подтверждает только его сборки и проверки.
Тестовая job в ручном workflow сама
собирает пакет и тестовый bundle через `xcodebuild build-for-testing`, затем
запускает `test-without-building`; артефакты сборки
между jobs не передаются.

UI-матрица делит `Tests/expected-ui-tests.json` через `scripts/split-ui-tests.py`:
каждый сценарий входит ровно в одну часть. Каждая job имеет собственные runner,
HTTPS-стенд, симулятор и артефакт `webkit-tests-<часть>-<попытка>`; внутри части
тесты остаются последовательными. `fail-fast: false` позволяет собрать результаты
всех частей даже при падении одной. Полный UI-прогон подтверждён только тогда,
когда все четыре части завершились успешно и каждая сверена со своим манифестом.
В текущем манифесте 33 сценария. Четыре части содержат 9, 8, 8 и 8 тестов.
Оценка времени на runners требует отдельного прогона Actions.

Загрузка нового симулятора начинается перед `build-for-testing`, чтобы миграции
runtime шли одновременно со сборкой. Перед тестами скрипт дожидается `bootstatus`
и устанавливает синтетический CA. В `timings.json` сохраняются начало, длительность
и результат этапов; каждые 30 секунд в логе виден текущий этап. `simulator-ready`
измеряет оставшееся ожидание после сборки, а не полное время загрузки.
Сборка и тесты имеют отдельные `build.xcresult` и `tests.xcresult`.
Ошибка сборки не запускает тесты; исходный ненулевой код сохраняется.

Xcode и runtime выбраны явно; отсутствие окружения завершает проверку ошибкой,
а не переключает её незаметно на другую версию. Состав образа может меняться:
при обновлении сверяйте описания образов GitHub для
[Intel](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-Readme.md) и
[Apple Silicon](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-arm64-Readme.md)
и проверяйте весь workflow. Локальная проверка на другом Xcode не заменяет запуск Actions.

Права workflow — `contents: read`; секреты и Apple Developer signing не нужны.
Публикация релизов, TestFlight и настройка branch protection не выполняются.
Лимит проверки копий — 5 минут, каждой Xcode job — 30 минут.

## Pre-push и ручной CI

После клонирования подключите версионируемый hook:

```bash
bash scripts/install-hooks.sh
```

Установщик задаёт локальный `core.hooksPath=.githooks` для клона и его worktrees;
глобальный Git config не меняется. Другой настроенный hooksPath и исполняемые
hooks в стандартном каталоге он не заменяет: установка останавливается до изменения
конфига с предложением объединить hooks вручную. Шаблоны `*.sample` не мешают установке.
Нужны те же Xcode/runtime и инструменты, что для локальных команд ниже.
По умолчанию hook выбирает `/Applications/Xcode.app/Contents/Developer`;
`DEVELOPER_DIR`, `SIMULATOR_OS` и `SIMULATOR_DEVICE` можно задать явно.

Перед push hook последовательно выполняет полный `test-spm` и полный `test-ui`
для каждого уникального отправляемого коммита на вершине ссылки. Для этого
`git archive` создаёт временный снимок: незакоммиченные файлы и текущий HEAD
не подменяют отправляемый код, stash/checkout исходного дерева не используются.
Промежуточные коммиты истории отдельно не проверяются. Удаление ссылок не запускает
тесты; ветка и tag на один коммит не удваивают прогон. `UI_TEST_MANIFEST` сбрасывается,
чтобы переменная от локальной диагностики не сократила обязательный набор.

Ошибка любого набора блокирует push. Логи и `.xcresult` остаются в
`artifacts/ci/pre-push.<commit>.<suffix>/`, `commit.txt` содержит проверенный SHA.
Временный снимок и его DerivedData удаляются после завершения; это означает чистую
сборку при каждом push. Отдельные симуляторы и HTTPS-стенд убираются общим скриптом.
Коммиты не ждут тестов. Hook нужно установить в каждом клоне; локальный
`git push --no-verify` обходит его, поэтому он не является серверной гарантией.

Для тестов в GitHub: **Actions → Simulator tests — manual → Run workflow → выбрать ветку** либо:

```bash
gh workflow run simulator-tests.yml --ref add-ios-sdk-tests
```

Этот workflow выполняет SDK-тесты и все четыре UI-части на закреплённом
окружении CI. GitHub требует наличие workflow с `workflow_dispatch` в default
branch; до его попадания туда кнопка/dispatch могут быть недоступны.
Локальный зелёный прогон на другом Xcode не подтверждает ручной CI.

## Локальные команды

Нужны macOS, полный Xcode, принятая лицензия/установленные компоненты Xcode,
Python 3 с модулем ssl, OpenSSL CLI в PATH и iOS Simulator runtime.
Стенд использует стандартную библиотеку Python, дополнительных pip-пакетов нет.
Command Line Tools отдельно недостаточно.
Из корня репозитория:

```bash
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
python3 scripts/sync-sdk.py --check
bash scripts/ci.sh build-spm
bash scripts/ci.sh test-spm
bash scripts/ci.sh test-ui
bash scripts/ci.sh build-example
```

Это те же скрипты, которые использует CI. Они выбирают Debug, схему `CraftTalk`
для пакета и `Chat` в `Example/Chat.xcworkspace` для приложения.
SDK использует UIKit, поэтому тестирование через macOS `swift test` не подходит.

Чтобы явно использовать другой установленный симулятор:

```bash
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcrun simctl list devices available
SIMULATOR_OS=27.2 SIMULATOR_DEVICE='iPhone 18 Pro' bash scripts/ci.sh test-spm
```

Для выбранных сценариев совместимости (точный состав также проверяется):

```bash
UI_TEST_MANIFEST=Tests/ui-compatibility-tests.json SIMULATOR_OS=18.6 SIMULATOR_DEVICE='iPad (A16)' bash scripts/ci.sh test-ui
UI_TEST_MANIFEST=Tests/ui-compatibility-tests.json SIMULATOR_OS=17.4 SIMULATOR_DEVICE='iPhone 15' bash scripts/ci.sh test-ui
```

Без `UI_TEST_MANIFEST` выполняется весь UI-набор. Указанный JSON должен содержать
непустой список уникальных имён из основного манифеста; выбранный состав сохраняется
в `selected-tests.json`. Поднабор не считается полным прогоном. Команда `test-ui`
включает code coverage в `.xcresult`.

Для воспроизведения одной части UI-матрицы:

```bash
python3 scripts/split-ui-tests.py --count 4 --output-dir .build/ci/ui-shards
UI_TEST_MANIFEST=.build/ci/ui-shards/shard-2.json bash scripts/ci.sh test-ui
```

Не запускайте части одновременно в одном checkout: они используют общий
`Fixtures/Runtime` и DerivedData. В CI изоляцию обеспечивают отдельные jobs.

Скрипт по умолчанию ищет iPhone 16 с iOS 18.6. `EXPECTED_XCODE_VERSION=16.4`
в CI дополнительно проверяет версию Xcode; локально эта проверка включается
только при явном задании переменной. `DEVELOPER_DIR` не меняет глобальный `xcode-select`.

`test-spm` и `test-ui` берут тип устройства/runtime найденного симулятора и создают **новый**
одноразовый симулятор. Он устанавливает синтетический системный CA только туда,
запускает HTTPS-стенд на loopback и выполняет XCTest. После успеха, ошибки тестов
или обрабатываемого SIGINT/SIGTERM сервер останавливается, симулятор удаляется.
Существующий симулятор и хранилище сертификатов macOS не меняются.
Прямой запуск `xcodebuild test` без стенда завершит интеграционные тесты ошибкой;
для полного набора используйте `test-spm` или `test-ui`.

Example собирается с `CODE_SIGNING_ALLOWED=NO` и
`IPHONEOS_DEPLOYMENT_TARGET=15.0`, переданными **только в командной строке**.
Override нужен для сборки старых targets приложения/Pods современным Xcode;
он не меняет настройки в Git и заявленный минимум SDK. Полученная сборка
не доказывает поддержку iOS ниже 15. Удалить override можно после отдельного
согласованного обновления deployment settings и зависимостей с проверкой сборки.
Используются закоммиченные Pods, `Podfile.lock` и `Pods/Manifest.lock`;
`pod install`/`pod update` для CI не нужны. Общая схема `Chat` хранится в Git.

## XCTest пакета

`CraftTalkTests` использует `@testable import CraftTalk`. Основной манифест
содержит 72 сценария. Таблица с распределением и границами проверок есть в
[плане покрытия](testing-plan.md).

- Изолированные тесты проверяют политику хостов и roots, сериализацию посетителя,
  построение push-запроса, диагностику и поиск ресурсов в Bundle.
- Сетевые тесты используют штатный `CTNetworkManager` с системным доверием
  одноразового симулятора. Для каждого сценария стенд даёт отдельный UUID,
  маршруты и журнал. Тесты отслеживают каталоги своих загрузок и удаляют их
  после проверки. Они подтверждают реальный GET/POST, cookies и возврат данных.
- TLS-тесты получают настоящие challenges через URLSession и передают их
  штатному `CTTrustEvaluator` из тестового делегата. Это проверяет сам оценщик.
  Доставку challenge от WebKit по публичному пути покрывает UI-набор.
  Отдельные тесты синтетического challenge проверяют ветвление без TLS-соединения.

## Локальный HTTPS-стенд

[Стенд](../scripts/https-fixture.py) создаёт синтетические корни, intermediate
и leaf на каждый прогон. Отдельный CA устанавливается в хранилище одноразового
симулятора для системного доверия. Другой CA передаётся через
`trustedRootsByHost`. TLS-соединения используют текущее время, а изолированная
проверка SecTrust использует фиксированную дату прогона и запрещает сетевой поиск
intermediate. Случай отсутствующего intermediate использует отдельную цепочку.

Порты выбирает ОС. Сокеты слушают только `127.0.0.1`. Запросы идут к
`localhost` и `127.0.0.1` без изменения DNS и файла hosts. Журнал фиксирует
метод, тело и заголовки синтетических запросов. Удерживаемые ответы ждут
явного `release` до 15 секунд в режиме `hold` и до 30 в `holdAfterHeaders`.
По таймауту стенд прерывает ответ, сохраняет ошибку в
`fixture-errors.json` и завершает прогон ненулевым кодом. `reset` и остановка
отменяют ожидания, сохраняя предыдущие ошибки стенда.

Секретные ключи остаются во временном каталоге процесса до уборки.
Публичные DER и конфигурация портов пишутся в игнорируемый
`Tests/CraftTalkTests/Fixtures/Runtime/`. Скрипт создаёт этот каталог только
при его отсутствии. После SIGKILL или аварии проверьте, что прогон остановлен.
Убирайте только оставшийся Runtime, временные файлы этого прогона и его
симулятор по UUID из `fixture.json`.

## WebKit UI-тесты

`test-ui` собирает схему `CraftTalkUIHost`. Приложение компилирует
канонический `CTChat/` и имеет собственный Info.plist. Xcode-проект и схема
есть в Git. `project.yml` описывает проект для обслуживания через XcodeGen.
Минимум iOS 15 относится к тестовому host.

Host вызывает публичные `configure(security:)` и `configure()`, затем
ставит барьер на публичной `ctqueue`, чтобы дождаться асинхронного чтения
Info.plist перед регистрацией посетителя и открытием контроллера.
Оба режима передают в WebKit явно заданный `hash`. Legacy загружает тестовый
leaf из ресурса `CTCertificate.der`, secure использует корни по хостам.
Только сценарий push задаёт непустой токен и проверяет POST, отправленный SDK.
Для `tel:` и `mailto:` тестовое приложение наблюдает вызовы UIApplication
без фактического звонка или отправки письма.

Тестовое приложение читает состояние JS, HTTPS-журнал, файлы и состояние
интерфейса. Оно использует штатные delegates, JS-мост и контроллер SDK.
Наблюдатель помечает существующие кнопки blob-предпросмотра для XCUITest,
сохраняя их actions. Сценарии проверяют байты скачанного WKDownload,
выбор файла и повторное открытие предпросмотра, введённый черновик и реальную
доступность поля ввода, фон/возврат и поворот. Перед запуском каждого сценария
host очищает cookies, WebKit-данные и тестовые остатки в своём контейнере.
Для WKDownload проверки удаления файла и каталога выполняются до этой уборки.
Прямые tmp-файлы blob-предпросмотра наблюдаются отдельно. Известные ограничения
исходного SDK и границы сценариев описаны в [плане покрытия](testing-plan.md).

Полный UI-манифест содержит 33 сценария. Манифест совместимости включает 7
из них. Его можно запустить на iPad (A16) с iOS 18.6 или iPhone 15 с iOS 17.4
командами выше. Такие запуски подтверждают только выбранные сценарии.

## Проверка состава наборов

Манифесты [SPM](../Tests/expected-tests.json) и [UI](../Tests/expected-ui-tests.json)
перечисляют обязательные сценарии. [Проверка результатов](../scripts/verify-test-results.py)
сверяет итоговую сводку и идентификаторы в дереве `.xcresult`, требует ровно
одно успешное выполнение каждого и отклоняет пропуски и expected failures.
При изменении состава обновите манифест, соответствующую матрицу и таблицу в
[плане покрытия](testing-plan.md). Диагностический UI-поднабор проверяется по
выбранному манифесту. Полный прогон в CI требует успеха всех четырёх частей.

## Синхронизация SDK

Источник истины — `CTChat/`. Копия — `Example/Chat/CTChat/`.

```bash
python3 scripts/sync-sdk.py --check
python3 scripts/sync-sdk.py --sync
```

`--check` ничего не меняет: сравнивает относительные пути и байты всех `.swift`,
сообщает об отсутствующих, отличающихся и лишних файлах и возвращает ненулевой
код при расхождении. В CI используется только этот режим.

`--sync` добавляет отсутствующие и обновляет отличающиеся файлы из корня.
Перед первой записью проверяет все изменяемые назначения: staged/unstaged
изменения, удаления и существующие untracked-файлы нельзя перезаписать.
Назначения с флагами Git `assume-unchanged` или `skip-worktree` также нельзя
перезаписать: команда прекращает работу до первой записи и не снимает флаги.
Если в копии есть лишние Swift-файлы, команда прекращает работу; их нужно
разобрать и удалить явно вместе со ссылками Xcode. Символические ссылки
в каталогах SDK не поддерживаются. Совпадающие файлы не переписываются.

Для новых Swift-файлов отдельно добавьте ссылки в проект Example и
Compile Sources target `Chat`: скрипт не редактирует `.pbxproj`.
Не используйте reset/checkout для обхода защиты локальных изменений.

## Диагностика и проверка ошибок

Каждая команда создаёт отдельный каталог в `artifacts/ci/` с полным
`output.log`, `.xcresult`, а для тестов — списком симуляторов, JSON-сводкой
и деревом выполненных тестов, в том числе при падении `xcodebuild`, если `.xcresult`
успел сформироваться.
Для сети добавляются `fixture.json` (UUID симулятора/runtime/порты/дата)
и `server-requests.jsonl` с синтетическими запросами, а также `fixture-errors.json`
с ошибками ожидания release (пустой список при отсутствии ошибок). Приватные ключи не попадают
в артефакты. Код ошибки `xcodebuild` сохраняется после очистки стенда.
`ARTIFACTS_DIR` позволяет выбрать другой каталог. Повторные запуски не стирают
старые результаты. DerivedData находится в `.build/ci/` и не загружается как артефакт.
Не запускайте локальные SPM build/test одновременно: они используют общий DerivedData.
`test-spm` и `test-ui` также нельзя запускать одновременно в одном worktree: оба
временно создают `Fixtures/Runtime/`; второй запуск откажется его перезаписывать.

GitHub Actions загружает диагностику через `if: always()` и хранит 14 дней,
в том числе при ошибке сборки или теста. При ошибке до создания `.xcresult`
останется текстовый лог; при принудительной остановке runner загрузка не гарантируется.
`pipefail` сохраняет ошибку команды при выводе через `tee`. Предупреждения
старого кода остаются видимыми и сами по себе не превращены в ошибки.

Команда проверки Python-инфраструктуры

```bash
python3 -m unittest discover -s scripts/tests -v
```

Python-проверки охватывают барьеры стенда, ошибки сборки/тестов, сохранение
кодов возврата и диагностики, очистку после ошибок, разбиение UI-набора
и работу hook на временных репозиториях. Для сверки XCTest есть проверки
успешного прогона, пропусков, дублей и подмены идентификаторов.
Проверки симуляторных результатов
используют сводку и дерево из `.xcresult`. Ошибка сборки сохраняет лог,
а при ошибке теста экспортируется и диагностика сформированного `.xcresult`.

Сверить саму поставку можно по списку файлов PR. Производственные команды
`build-spm` и `build-example` собирают исходные targets, а запуск тестов
использует свой проект и ресурсы. Проверки локального Xcode не подтверждают
выполнение workflow на закреплённых GitHub runners.
